# Operational observability and redaction

Facturations emits one bounded operational event per completed HTTP request so incidents can be correlated without turning logs into a second copy of customer data.

## Request correlation

A UUID v4 request ID is generated by the server for each request.

- incoming `X-Request-ID` values are ignored;
- the server ID is returned as `X-Request-ID`;
- a caller therefore cannot inject log text or choose the correlation identifier.

## Structured request event

The emitted JSON contains only:

- UTC timestamp;
- `event = http_request`;
- server-generated request ID;
- HTTP method;
- normalized route group;
- HTTP status code;
- bounded duration in milliseconds;
- outcome `finished` or `closed`.

Dynamic paths are converted to constant groups such as:

- `PORTAL_ACCESS`;
- `PORTAL_INVOICE`;
- `PORTAL_PDF`;
- `WORKSPACE_ITEM`;
- `REVIEW_ITEM`;
- `API_DRAFT_ITEM`.

Unknown paths become `OTHER`.

## Data that must never enter operational request logs

This telemetry intentionally does **not** record:

- raw URL;
- query strings or magic-link tokens;
- UUIDs from routes;
- email addresses or customer names;
- request or response bodies;
- cookies or session tokens;
- Authorization / admin / CSRF headers;
- IP address;
- User-Agent;
- database URL or SQL errors;
- raw exception messages;
- PDF content;
- invoice content;
- Wave/payment/email provider secrets.

The telemetry observer never consumes the request body and never changes authorization decisions.

## Failure behaviour

Operational logging is best-effort:

- failure of the log sink cannot change an HTTP response;
- an invalid internally generated request ID disables that event instead of emitting unsafe data;
- a prematurely closed connection emits a bounded `closed` event once;
- `finish` and `close` cannot produce duplicate entries.

## Production requirements still external

This repository establishes safe event shape and correlation. Before production, operations must still define:

- log destination and encryption;
- access control;
- retention/deletion period;
- alert rules and paging destination;
- dashboard ownership;
- clock synchronization;
- log availability/health monitoring;
- incident escalation;
- rules preventing downstream log processors from enriching events with sensitive request data.

Do not enable generic reverse-proxy access logs containing full URLs for the client portal unless they are independently configured to redact query strings and dynamic identifiers.
