# Browser staff login — opt-in staging feature

A compact responsive French/English sign-in form at `GET /internal/login?lang=fr|en` collects invited staff email, password and six-digit authenticator code. `POST /internal/login` verifies an exact configured HTTPS Origin and Host, same-origin Fetch Metadata when present, strict bounded form fields, and the per-email PostgreSQL limiter **before** authenticating. The staff store requires correct password AND an activated, one-time TOTP before inserting a session. Only successful sign-in sets a host-only `__Host-facturations-session` cookie (`Secure; HttpOnly; SameSite=Strict; Path=/`) and redirects to the read-only `/internal/dashboard`. A failed reset revokes the newly issued session without exposing its token. `POST /internal/logout` checks Origin and revokes that cookie's session; it clears the cookie and redirects to login. Cookies NEVER authorize protected `/api/*` endpoints or permit Wave/invoice writes. They **do** authorize private `/internal/workspaces` routes with separate session, business and staff-ownership checks; writing to a workspace also requires exact Origin/Host and a session-bound anti-CSRF token. No registration, email send or invoice issuance is added.

This login and the private workspace routes are ABSENT unless a separate Facturations PostgreSQL database (`FACTURATIONS_DATABASE_URL` and `WAVE_BUSINESS_ID`) and both private server environment variables are provided:

- `FACTURATIONS_PUBLIC_ORIGIN`: exact externally accessible HTTPS origin, for example `https://facturations.example.test` (fictional placeholder, NOT a deployed URL). No path or trailing slash.
- `FACTURATIONS_TOTP_ENCRYPTION_KEY`: independently generated random 32 bytes encoded as 64 hex digits, held privately by the server; never commit, log or send to the browser. Its loss prevents decryption; rotation and recovery must be planned.

Migrations **001–008** must be applied in numeric order ONLY to the new, dedicated Facturations database, with suitable roles and backups. Migration 008 is necessary because `app.js` installs the workspace routes together with browser login when the environment variables above are present; there is no independent `NODE_ENV=development` gate. Accounts are only created through **trusted, verified enrollment**; no unauthenticated invitation or account-creation route exists. A TOTP secret must be securely provisioned and activated before a staff member can sign in. The separate PostgreSQL limiter must be retained across process restarts and its expired rows safely pruned in a future maintenance job.

**Deployment is still blocked:** MochaHost must confirm a dedicated isolated app and trusted TLS reverse proxy that strips untrusted forwarding headers, ensures the Node port is not directly exposed, preserves the canonical Host, and adds trusted-edge per-IP throttling. Before accepting real users, verify migration rollout, secret rotation/recovery and approved account enrollment; run real end-to-end staff login/logout, rate-limit, browser cookie, workspace CSRF/revision, CSP, cross-tenant and accessibility tests on an independent staging host. Complete the dashboard's visible logout control and monitoring/backup/restore checks. No existing GROUPE TAKATAK production website, database or Wave business may be changed as part of this step.
